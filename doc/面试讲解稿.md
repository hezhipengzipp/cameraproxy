# 面试讲解稿：CameraProxy 项目

> 面试可直接套用的「**一句话定位 → 业务场景 → 技术难点 → 可能追问**」四层结构。
> 对照代码位于 `server/` 和 `client/` 模块。

---

## 一、30 秒电梯版（面试官问"介绍下你的项目"）

> **这是一个解决 Android 相机共享问题的跨进程框架。**
>
> 背景：Android Camera2 架构上，**同一台设备同一时刻只能被一个 CameraDevice 实例独占**，一个 App 没办法让多个模块并发消费同一路相机流；即使塞进同一个 App，CaptureSession 的 Surface 数量也受硬件级别限制，通常 3 路就顶到天花板。
>
> 我做的方案是：**把相机挂在一个独立进程的前台 Service 里独占使用，对外通过 AIDL 暴露订阅接口，用 OpenGL 的 fan-out 机制做零拷贝分发**。任何 App bind 上来、传一个 Surface 进来，就能拿到和相机 HAL 同步的画面流；订阅者增减不重建 CaptureSession —— 没有黑屏闪烁，也不经过 CPU 内存拷贝。

---

## 二、业务场景 —— 为什么这东西**非做不可**

这是面试官最爱问的"你这项目解决什么**真实**问题"。准备 3 个**场景化**回答，任选一个最贴近应聘岗位的讲：

### 场景 A：车载 / 辅助驾驶（最硬核，优先用）

一颗前置摄像头要同时供给：

- **ADAS 模块**（车道偏离、前碰撞预警） —— 要实时 YUV
- **DMS 驾驶员监控**（疲劳、分神识别） —— 要人脸算法
- **行车记录仪**（1080P 录制 + 编码）
- **HUD 或中控屏幕预览**

这些可能来自 **不同供应商的 App**（甚至不同进程）。不做共享方案，要么多个 App 互相抢相机导致黑屏，要么只能牺牲某个功能。

### 场景 B：直播 / 视频会议 SDK

宿主 App 要预览 + 推流，SDK 要做美颜 / 抠像 / AI 特效 / 本地录制。传统做法是 SDK 代理整条相机链路，主 App 失去控制权。用这个框架，**SDK 和主 App 都作为订阅者**，各取一路。

### 场景 C：安防 / 门禁 / IoT 设备

一路摄像头同时：本地 AI 识别（人脸、物体）+ 主画面预览 + RTSP 推流 + 云端录像。以前靠 HAL 定制，现在应用层就能做。

### 一句话升华

> **本质上这不是"给相机加功能"，而是把"Camera 资源"从"独占资产"变成"共享服务"**，像 Display 系统那样，多 App 自由订阅。

## 三、技术难点 —— 讲清楚这 6 个，技术深度就够了

### 难点 1：**零拷贝的分发机制（最核心）**

**坑**：朴素做法是在 Service 里用 ImageReader 拿 YUV buffer，再用 Binder 传给订阅者 App。问题：

- Binder 传输有 1MB 限制，1080P YUV 单帧就 3MB，直接挂
- 就算分片传，每帧 CPU 拷贝 + Binder 序列化 + 对方再拷贝，30 fps 下 CPU 吃满
- 电量灾难

**我的方案**：用 **OpenGL fan-out**：

```
Camera2 → 唯一的 SurfaceTexture → OES 纹理
                                      ↓
                for each 订阅者 EGLSurface:
                    eglMakeCurrent(订阅者 Surface)
                    glDraw(OES 纹理)
                    eglSwapBuffers   ← 直写订阅者的 Surface，跨进程零拷贝
```

关键点：**订阅者传进来的 `android.view.Surface` 在 Server 端通过 `eglCreateWindowSurface` 变成 EGLSurface**，GL 画到这个 EGLSurface 的结果，**由 BufferQueue 机制直接送回订阅者进程**，全程是 GraphicBuffer 在 GPU/DMA 侧流转，CPU 完全不参与。

### 难点 2：**动态增减订阅者不能扰动正在运行的相机**

**坑**：Camera2 的 `CameraCaptureSession` 一旦创建，输出 Surface 列表是**固定**的。想加订阅者就得 `createCaptureSession` 重建 —— 必然黑屏几百毫秒。

**我的方案**：CaptureSession **永远只挂一个固定的 SurfaceTexture**，订阅者数量变化只改 GL 侧的 EGLSurface 集合。所以 **CaptureSession 在整个 Service 生命周期内只创建一次**。

### 难点 3：**三线程协同 —— 线程归属的纪律**

```
┌─ Binder 线程池   —— AIDL 方法入口
├─ camera 线程     —— CameraDevice / CaptureSession 回调
└─ gl 线程         —— 唯一持有 GL context 的线程
```

**纪律**：

- **所有 GL 调用只能在 gl 线程**（EGL context 绑线程的）
- **Binder 方法切 GL 线程必须同步等完**（否则 `addSubscriber` 返回了 EGLSurface 还没建好，下一个 subscribe 就乱了）
- 所以写了个 `runOnGlThreadBlocking` 用 `CountDownLatch` 把异步 post 封成同步

讲得再细一点可以提：Camera2 的 API 全异步，用 `CountDownLatch` + StateCallback 封成同步的 `openCamera()`，外层代码才好写。

### 难点 4：**客户端进程异常退出的自愈**

**坑**：订阅者进程崩了 / 被 LMK 杀了，**不会**走 `unsubscribe`。Server 侧如果不清理，EGLSurface 泄漏、记录永远在 map 里。

**我的方案**：利用 Binder 的 `linkToDeath` 机制。

```kotlin
callback.asBinder().linkToDeath(deathRecipient, 0)
// 客户端进程死掉，deathRecipient.binderDied() 在 Binder 线程自动触发
// 内部走和主动 unsubscribe 完全一致的清理路径
```

这里体现两个设计点：

- **主动退订 / 被动死亡** 两条路径**共用同一个 internalUnsubscribe**，保证清理逻辑只有一处；
- 最后一个订阅者退出时自动 closeCamera 省电。

### 难点 5：**相机帧的反压 —— BufferQueue 不能堵**

**坑**：SurfaceTexture 内部是个 BufferQueue，如果我们不 `updateTexImage` 把帧消费掉，Camera2 会被阻塞，下一帧丢、掉帧率。

**我的方案**：即使暂时没有订阅者，也要把帧"吞掉"。做法是预建一个 1x1 的 **dummy Pbuffer Surface**，每次 `onFrameAvailable` 先 `makeCurrent` 到 dummy 上调 `updateTexImage`。这样 SurfaceTexture 永远能消费完。

### 难点 6：**OES 纹理 + SurfaceTexture 的各种"暗坑"**

- OES 纹理**不支持** `GL_REPEAT`，只能 `CLAMP_TO_EDGE`
- OES 纹理**不支持 mipmap**，只能 `GL_LINEAR` / `GL_NEAREST`
- Shader 必须 `#extension GL_OES_EGL_image_external : require`，采样器类型是 `samplerExternalOES` 而不是 `sampler2D`
- 相机输出的纹理坐标**天然是翻转的**，必须每帧调 `getTransformMatrix()` 拿 4x4 修正矩阵，在 Shader 里乘上 —— 不乘就画面上下颠倒

这些不是抄代码能发现的，是踩坑踩出来的 —— 讲出来显示确实动过手。

## 四、可能的追问 —— 提前想好

### Q1：**为什么不用 ImageReader + Bitmap 传？**

> 刚讲过 —— Binder 1MB 限制 + 拷贝开销 + 30 fps CPU 吃满。GL fan-out 走 BufferQueue + GraphicBuffer，GPU 侧直接映射，纯硬件路径。

### Q2：**Android 原生不是有 `CameraManager.registerAvailabilityCallback` 之类 API 吗？**

> 那只是**设备可用性**通知，不是流共享。原生 Camera2 没有多客户端流分发能力，HAL 层面也只允许一个 CameraDevice 独占。

### Q3：**同一进程多 Surface 挂到 CaptureSession 不就行了？**

> 有三个硬限制：① `CameraCaptureSession` 的 Surface 组合受 `INFO_SUPPORTED_HARDWARE_LEVEL` 限制，通常 3 路已经到上限；② 不支持**跨进程**订阅；③ 改订阅者组合要重建 Session，黑屏。

### Q4：**Android 14 前台服务新限制你怎么处理的？**

> `android:foregroundServiceType="camera"` + 运行时 `startForeground(id, notif, FOREGROUND_SERVICE_TYPE_CAMERA)`，并声明 `FOREGROUND_SERVICE_CAMERA` 权限。低版本走旧 API。

### Q5：**多个订阅者画面尺寸不一样怎么办？**

> 每个订阅者的 EGLWindowSurface 尺寸由 Client 侧 SurfaceView 决定。Server 在首帧绘制时用 `eglQuerySurface` 查真实尺寸，`glViewport` 按该尺寸设置 —— **Shader 固定画 `[-1,1]` 全屏四边形，视口自适应**，所以同一个纹理能自然贴合不同尺寸。

### Q6：**性能怎么样？能达到多少路并发？**

> 取决于 GPU 带宽。实测常见手机 1080P @ 30fps 下跑 4-5 路订阅者 CPU 占用 <5%，功耗增量主要是多几次 eglSwapBuffers。瓶颈不在 CPU 而在 GPU 填充率。

### Q7：**HAL 自己不能做这事吗？**

> 能，但要改厂商代码、不通用、App 层无权介入。这个方案是**纯应用层**的，不依赖 ROM 定制，只要设备支持 Camera2 就行。

### Q8：**跟 MediaCodec 的 Surface 输入有什么异同？**

> 异曲同工 —— 两者底层都是 BufferQueue + GraphicBuffer + OES。MediaCodec 把 Surface 当输入（编码），本项目把订阅者 Surface 当输出（显示 / 二次消费）。如果订阅者是 MediaCodec 的输入 Surface，**Server 画一次、直接喂编码器**，又是一个零拷贝链路。

### Q9：**有没有考虑用 Shared Memory / AHardwareBuffer？**

> 这是进阶话题，可以说：
>
> - **AHardwareBuffer** 是 Android 8+ 引入的跨进程共享 buffer 原语，理论上能更通用
> - 本项目用 Surface + BufferQueue 本质上底层就是 AHardwareBuffer，只是封装在更熟悉的 API 里
> - 直接用 AHardwareBuffer 要自己管理同步栅栏（fence）、格式转换，复杂度陡增
> - 所以**在项目阶段选择了 Surface 路线**，把工程复杂度控制住

## 五、最后一层 —— 怎么升华

如果面试官说"你讲得不错，那这个项目让你学到最重要的事是什么？"，可以这样收尾：

> 这个项目让我对 **"约束驱动设计"** 有了体会：
>
> Camera2 不能多路分发、Binder 不能传大数据、GL context 绑线程 —— 这些看起来都是**限制**，但真正把它们拼在一起解决问题时，每一条限制其实都在**引导正确的架构**：独占相机 → 必须独立进程；不能传大数据 → 必须让数据走 GPU 管线；GL 绑线程 → 必须严格线程纪律。
>
> 最终的方案很**紧凑**，没有冗余，每一块都有不可替代的理由 —— 这是我觉得它值得拿出来讲的原因。
